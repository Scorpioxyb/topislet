# v0.1.3 日常体验优化计划

目标版本：`v0.1.3-dev`

App 版本：`0.1.3 (30)`

发布方式：GitHub DMG 开发预览版，继续使用 ad-hoc 签名；开发阶段不创建 Tag、不推送 GitHub Release。

## 版本目标

v0.1.3 先用真实日常日志识别和修复现有音乐体验问题，不扩展新的音乐应用、计时器、通知或歌词。汽水音乐继续作为主适配，Apple Music 与网易云音乐维持现有 Alpha 边界。

## P0

- 每个已接受的 seek 最终进入确认、超时或取消之一；连续拖动覆盖、切歌、来源切换、播放器退出和 App 停止均留下结构化原因。
- 正常 seek 取消不算异常，但计入样本终态覆盖；已接受 seek 缺少任何终态时日报必须保持 `partial`。
- 日报继续只记录来源标签、匿名延迟、目标千分比和取消原因，不记录歌名、歌手、歌词、封面、账户或文件路径。
- 不增加媒体轮询，不改变来源仲裁、PID 定向控制、汽水 seek 安全门禁或岛内进度条行为。

## 后续 P0 候选

完成首个可观测性修复并积累新的日常样本后，只对真实越线项排期：

- 切歌文本、歌手与封面原子收敛延迟。
- 播放 / 暂停权威确认延迟和进度冻结一致性。
- seek 确认延迟、超时率以及非预期取消比例。
- 来源切换抖动、退出回退和多媒体并存误控。

## 阶段

1. M0（完成）：审计最近 24 小时真实日志，冻结范围和首个 P0。
2. M1（完成）：补齐 seek 取消终态、原因聚合和日报 schema 4。
3. M2（完成）：安装 Release build 24；20/20 个真实 seek 具备终态，确认 9、超时 0、正常覆盖取消 11，样本完整且无异常。
4. M3（完成）：build 29 已完成隐私安全的四阶段诊断和 20 次主动实机切歌。控制派发 P95 保持 `12ms`；首个候选包 P95 `116ms`，但 20/20 仍含原子门禁必须拒绝的过渡状态；首个可信完整包 P95 `654ms`，完整包到 UI 仅 `12ms`。瓶颈已定位到汽水 / MediaRemote 完整状态的到达时间，`500ms` 收敛门槛尚未关闭。
5. M4（完成）：build 30 修复汽水实时歌曲状态与 AX 控件可用性分裂导致的三键灰化；统一按已验证汽水 PID 解析运行实例，并在实时状态恢复时重建控件可用性。安装版命令级回归确认播放 / 暂停 2/2、上一首和下一首各 1/1 均接受；切歌在 220ms 仍处于汽水过渡包时不提前发布，约 3 秒后完整状态收敛。详见 `Docs/acceptance/2026-09-04-v0.1.3-qishui-three-control-runtime.md`。
6. M5（下一项）：继续处理汽水完整曲目状态 P95 超过 500ms 的 P0。只寻找更早且能绑定汽水 PID 与完整曲目身份的直接证据源；保持原子发布门禁，不用新歌名搭配旧歌手、专辑、时长或封面来换取表面速度。

## 明确不做

- 新音乐应用适配。
- 计时器、日历、提醒事项和第三方消息通知扩展。
- 歌词来源扩展。
- Windows 版本。
- 大规模拆分 `main.swift` 或重写媒体底层。
