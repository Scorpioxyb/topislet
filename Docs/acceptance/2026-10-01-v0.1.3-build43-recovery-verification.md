# v0.1.3 build 43 恢复判定修复检查点

阶段 0 仍未完成。此检查点修复代码和通过自动检查，不代表恢复流程已经实机验收。

## 问题与改动

build 42 每 0.5 秒刷新时以 `controlRecoveryAction == nil` 作为恢复结束条件。汽水重启过程中暂时未运行、权限不可用或 UI 来源变化，也可能没有恢复入口；因此该条件不能证明三键已恢复，会提前取消正在进行的恢复任务。

回归测试先复用旧判定，确认 `.notRunning` 与 `.accessibilityRequired` 两例失败，然后修正：

- 恢复开始及重启返回后清除旧 AX 验证、缓存与待完成的旧探测代次。
- 启动完成前保持恢复状态；完成后只有汽水独立可用性为 `.available` 才报告“控件已恢复”。此值来自语义 AX 的唯一控制组验证，与当前 UI 恢复入口是否存在无关。
- 等待期间入口消失不取消任务；沿用原有有限检查周期，未通过时报告恢复失败。
- 顶屿停止时取消恢复任务；汽水重启等待和重试在取消后不再提交后续启动请求。已经提交给 LaunchServices 的启动请求不承诺可以撤回。
- 打包脚本增加 `LAUNCH_AFTER_INSTALL=0`，允许锁屏时安装而不执行启动 UI 操作，默认行为不变。

此漏洞有代码与失败测试证据，但尚未证明它是 build 42 `scanned=2 / candidateCount=0` 的唯一原因。不能把这次改动解释为稀疏 AX 树已经恢复。
