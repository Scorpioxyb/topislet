# v0.1.3 汽水三键运行态回归

日期：2026-09-04

分支：`main`

App：`0.1.3 (30)`，安装路径 `/Applications/顶屿.app`

## 范围与边界

本轮只验证安装版实际使用的汽水语义 AX 控制路径，不启动 Apple Music、网易云音乐、抖音、浏览器或其他音频来源；不使用 Computer Use，不发送全局媒体键，不激活汽水窗口，不移动鼠标。

## 控件树基线

- `--adapter-status`：汽水来源已验证，`sourceBundleIdentifier=com.soda.music`，状态流有有效曲目、播放态、进度、时长和封面。
- `--qishui-control-diagnostic`：辅助功能已授权，唯一候选播放控制组 `candidateCount=1`；控件容器位于汽水底部播放器区域，`relativeY=0.955`。
- `--qishui-control-availability`：回归开始前为 `available`，允许控制。
- AX 控件按汽水语义播放组的横向顺序绑定上一首、播放 / 暂停、下一首；本轮没有修改该映射。

## 长窗口结果

| 操作 | 结果 | 观察 |
| --- | --- | --- |
| 播放 / 暂停 | `2/2` 接受 | 播放中立即切为暂停，暂停后等待约 2 秒仍保持冻结；再次操作立即恢复播放 |
| 下一首 | `1/1` 接受 | 220ms 内出现汽水过渡包；约 3 秒后歌名、歌手、专辑、时长和封面均为同一完整状态 |
| 上一首 | `1/1` 接受 | 220ms 内出现汽水过渡包；约 3 秒后歌名、歌手、专辑、时长和封面均为同一完整状态 |

切歌的 220ms 结果曾出现“新歌名 + 旧专辑 / 旧封面”等过渡字段，这是汽水上游正在重建状态的中间包。顶屿现有原子门禁不会把该包发布为完整歌曲；因此 220ms 回读不能判定切歌失败，必须等待可信完整包。

## 安全与结束复核

- 三次控制均由汽水 PID 内唯一语义 AX 控件接受；控制命令没有切换前台应用，也没有增加音频来源。
- 回归结束后检查到汽水主窗口处于关闭 / 隐藏状态，AX 只剩稀疏根节点：`scanned=2`、`candidateCount=0`、`controlAvailability=controlTreeUnavailable`。这是安全拒绝状态：进程和汽水专属状态流仍可存在，但没有可验证的播放控件时不应继续提供控制。
- 回归期间和结束复核未发现 `SkyComputerUseService`、`CUALockScreenGuardian`、`QishuiProbe` 或额外控制进程残留；顶屿保持一个主进程和两个预期只读状态流。

## 结论

build 30 的汽水三键可用性恢复和长窗口语义控制回归通过，不需要修改控件横向映射。切歌完整状态仍受汽水 / MediaRemote 上游到达时间限制；“完整状态 P95 不超过 500ms”继续作为 v0.1.3 M5 P0，不能用混合元数据提前发布来关闭。
