# v0.1.3 汽水切歌阶段延迟验收

日期：2026-09-01

分支：`codex/v0.1.3-development`

App：`0.1.3 (29)`

## 目标与隐私边界

把汽水切歌链路拆为 `control_result → first_candidate → atomic_complete → ui_published`，判断剩余约 0.64 秒来自顶屿内部等待还是汽水完整状态到达时间。

阶段事件仅记录匿名 transition ID、阶段名、累计延迟、是否触发原子 defer，以及歌手、专辑、时长和封面是否存在。日志不记录歌名、歌手、专辑、歌词、封面内容、账户或路径；没有增加 MediaRemote、AX、Apple Event 或其他媒体轮询。

## 实施与回归

- 已接受的汽水上一首 / 下一首控制创建一次匿名阶段观察；播放 / 暂停和其他音乐来源不进入本诊断。
- 状态流首次出现不同曲目身份时记录 `first_candidate`；只有现有原子门禁确认未混用上一首字段时才记录 `atomic_complete`。
- 实际 UI 接受完整新曲状态后记录 `ui_published` 并结束该 transition，快速连续控制会用新 transition 替换旧观察。
- 新增单元测试确认过渡包只产生匿名字段完整性和延迟，完整包随后产生原子完成事件。
- `swift test`：223 项通过。

## 结论

- 顶屿在控制完成约 0.1 秒后已经收到新曲候选，但候选仍携带会触发原子门禁的过渡状态，不能安全发布。
- 第一个可原子发布的完整状态在本轮 P95 `654ms` 才到；随后 UI 发布只增加 P95 `12ms`。当前主要瓶颈是汽水 / MediaRemote 完整状态的观察到达时间，不是按钮派发、SwiftUI 更新或岛动画。
- build 27 已验证把同步补取起点从 180ms 提前到 40ms 仍无收益；本轮不再缩短内部等待，也不发布新歌名搭配上一首歌手、专辑、时长或封面的混合状态。
- `500ms` 完整收敛门槛继续保持未关闭。下一步只能寻找比现有 MediaRemote 更早、且能绑定汽水当前 PID 与完整曲目身份的直接证据源。
