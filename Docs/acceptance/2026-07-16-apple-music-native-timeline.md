# 2026-07-16 Apple Music 原生时间线量化

## 目标

build 18 动态回归中，Computer Use 观察到跨专辑界面约 2.5 秒内完成切换，但单次界面采集本身约占 0.8 至 1 秒。本轮在顶屿内部增加纯内存、低开销时间线，直接测量控制命令、`com.apple.Music.playerInfo`、Apple Event 快照、封面读取、快照应用和 UI 发布，不再用外部截图时间推断内部延迟。

## 测试环境

- 顶屿：基于公开 build 18 的当前开发分支包，App `0.1.1 (18)`，安装于 `/Applications/顶屿.app`。
- Apple Music 与汽水音乐同时运行，Apple Music 自动化权限和汽水辅助功能权限均已授权。
- 时间线使用 `ProcessInfo.systemUptime` 记录单调时钟，不写磁盘、不上传数据、不增加刷新请求。
- 最多保留 4 条转换，每条最多 24 个事件；设置页只显示最近一条，复制诊断时包含完整历史。

## 岛内下一首

从 `Janice STFU - Drake` 切换到 `B's On The Table - Drake & 21 Savage`：

| 阶段 | 相对控制发出时间 |
| --- | ---: |
| 岛内下一首发出 | `0ms` |
| 定向 Apple Event 接受 | `169ms` |
| 第一次 timeline 快照开始 | `266ms` |
| `playerInfo` 新曲通知到达 | `267ms` |
| Apple 公共目录封面读取开始 | `267ms` |
| 封面就绪，`44503 bytes` | `372ms` |
| timeline 快照返回新曲 | `419ms` |
| 新曲与封面原子应用 | `419ms` |
| 岛完成歌名、歌手和封面发布 | `421ms` |

结果：控制发出到完整 UI 发布为 `421ms`。Computer Use 在约 0.9 秒首次采样时仍可能显示旧内容，但原生时间线确认顶屿已经在半秒内完成发布，外部采样不适合作为内部延迟计时器。

## 跨专辑外部切换

切换到 `玻璃 - Gareth.T`，封面与上一专辑不同：

| 阶段 | 相对 `playerInfo` 时间 |
| --- | ---: |
| `playerInfo` 新曲通知到达 | `0ms` |
| Apple 公共目录封面读取开始 | `0ms` |
| metadata 快照开始 | `76ms` |
| metadata 快照返回新曲 | `219ms` |
| 新歌名和歌手权威快照应用 | `220ms` |
| 不同专辑封面就绪，`89499 bytes` | `444ms` |
| 封面合并到缓存快照 | `447ms` |

结果：新曲权威元数据在 `220ms` 应用，不同专辑的真实封面在 `447ms` 合并。读取诊断前，来源选择已按前台状态回到汽水，因此该条只量化 Apple Music 适配器链路，不把汽水 UI 发布记入 Apple Music 时间线。

## 技术结论

- build 18 的 Apple Music 内部切换不是 2.5 秒级；本机完整 UI 发布实测 `421ms`，跨专辑真实封面合并实测 `447ms`。
- 当前 `80ms` 首次控制跟进恰好让 timeline 快照在新曲通知前约 `1ms` 发起，并在通知后返回新曲。直接把首轮改成更密集或立即轮询，可能更早读回旧曲并增加 Apple Event 压力。
- 同专辑样本中封面比最终 UI 早 `49ms` 就绪；为这一级收益提前发布非权威 `playerInfo` 候选，会削弱现有原子快照和时间轴一致性，不值得在当前 Alpha 引入。
- 保留现有通知优先、低频轮询兜底和控制 refresh burst。时间线继续用于不同账号、电台、网络与设备环境收集证据，再针对真实慢段优化。
