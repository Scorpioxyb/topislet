# v0.1.3 汽水切歌控制延迟自动门禁

日期：2026-09-01

分支：`codex/v0.1.3-development`

App：`0.1.3 (28)`

## 目标与约束

主动操作顶屿完成汽水切歌样本，不等待产品负责人日常使用。测试期间只允许汽水音乐作为实际音频来源；不启动 Apple Music、网易云音乐、抖音或其他媒体，不发送全局媒体键，不增加媒体轮询，也不记录原始歌名、歌手、封面、账户或路径。

控制优化不能放宽安全边界：汽水 PID、辅助功能权限、唯一语义三键、窗口归属和控件健康仍由实际 `press` 路径完整校验；切歌显示继续保持歌名、歌手、专辑、时长和封面原子发布。

## build 24 基线

基线报告：`.build/qa/topislet-v0.1.3-auto-steady-20.json`，仅保留本机，不进入 Git。

| 指标 | P50 | P95 | 最大值 |
| --- | ---: | ---: | ---: |
| 控制派发 | 487ms | 569ms | 579ms |
| 控制到完整文本 | 1118ms | 1197ms | 1210ms |
| 控制到完整封面 | 1118ms | 1197ms | 1210ms |

20/20 控制接受，拒绝、误控、来源切换和未解决封面均为 0。事件时序显示协调器先执行完整可用性预检，随后实际 `press` 又执行一次安全校验，重复工作占据了大部分控制派发时间。

## 实施

1. 当协调器最近一次汽水控制可用性已经是 `.available` 时，点击路径跳过重复预检；未知、权限失效、窗口关闭、控件树异常和未运行状态仍必须重新预检。
2. 实际 `QishuiSemanticAXController.press` 保留完整 PID、权限、唯一控件、窗口和控件健康校验；失败后仍立即把可用性降为控件树不可用并安排恢复。
3. 汽水完整新曲状态发布后延迟 180ms 事件驱动刷新语义控件缓存，使 Chromium 切歌重建控件后下一次点击无需重新发现；这复用现有串行控制队列，不创建媒体轮询。
4. 曾将混合状态补取等待由 180ms 提前到 40ms 做 5 次 A/B，小样本完整发布 P95 仍为 648ms，没有收益，因此已撤回，最终 build 28 保持原补取策略。

## 最终主动实机门禁

最终报告：`.build/qa/topislet-v0.1.3-build28-final20.json`，原始结构化日志输入为同目录 `topislet-v0.1.3-build28-final20-log.json`；两者仅保留本机，不进入 Git。

通过 Computer Use 点击顶屿真实“下一首”控件，分两组各 10 次，每次保留约 3.2 秒稳态收敛时间。第二组开始前岛因悬停结束自动折叠，测试只重新展开岛后继续，没有把展开点击计入媒体控制样本。

本次报告的覆盖状态为 `partial`，仅因为定向切歌场景没有刻意制造 seek 或来源切换样本；20 个控制与 20 个完整曲目样本均齐全，不代表控制门禁缺样本。

## A/B 结论

- 控制 P95：`569ms → 12ms`，减少约 97.9%。
- 控制到完整文本和封面 P95：`1197ms → 649ms`，减少约 45.8%。
- `track_changed` 与 `ui_published` 在最终样本中同时发生，顶屿 UI 没有额外等待；剩余约 0.64 秒主要位于汽水完整可原子发布状态到达之前。
- 隔离原始状态流观察到切歌期间连续状态包；提前启动一次完整补取没有缩短最终发布，说明不能通过单纯降低补取等待继续获益。

因此，本轮“控制派发延迟”门禁通过；“完整文本与封面 P95 不超过 500ms”仍未通过，v0.1.3 切歌收敛 P0 保持打开。后续只能继续寻找更早且可验证的汽水专属完整状态证据，不能发布新歌名配旧歌手、旧专辑、旧时长或旧封面的混合状态。
