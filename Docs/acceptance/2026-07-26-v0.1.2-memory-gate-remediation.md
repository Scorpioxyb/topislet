## 结论

101 分钟旧安装版观察中 RSS 最终增长 `19.0%`，超过 `15%` 门槛，因此没有直接进入下一产品项。完成定位、两轮代码修复、全量测试、Release 安装和分阶段压力复测后，最终候选在暖态 30 次连续切歌中：

- RSS：`75,612,160 → 72,515,584 bytes`，最终 `-4.10%`，峰值 `+0.39%`。
- physical footprint：`25,543,592 → 26,526,632 bytes`，最终 `+3.85%`，峰值 `+5.84%`。
- CPU：平均 `0.034%`，P95 `0.046%`，最大 `0.067%`。
- 线程：基线 5、结束 6、最大 7，没有连续增长违规。
- 直接子进程：基线和结束均为 2，瞬时最大 3，最长增长 `10.0s`。
- 可见窗口始终为 1，主进程 PID 全程存活，30 次控制失败为 0。
- 监测摘要 `violations` 为空。

内存修复门禁通过，可以进入切歌元数据加载延迟优化。最终候选的完整 2 小时长稳仍保留为 GitHub 发布前验收项，本报告不把 5 分钟压力复测冒充为完整 2 小时测试。

## 定位证据

- `leaks` 仅报告约 `14,320 bytes` 的系统 AppIntents / XPC 循环，无法解释约 11 MB 的 RSS 增长，不能据此宣称存在已确认的应用层泄漏。
- 旧进程 `vmmap -summary` 的 physical footprint 约 `29.5MB`，Malloc 实际分配约 `12.1MB`，明显低于 RSS；说明 RSS 同时包含共享框架页与可回收驻留页。
- `AlbumArtworkImageCache` 原来最多保留 12 张原始封面数据和完整尺寸 `NSImage`，没有像素下采样或解码成本上限。
- 封面主色原来由全局 Core Image 上下文读取；高频切歌会加载 Core Image / Metal 路径并产生可清除图像分配。

## 修复内容

1. 封面进入 UI 缓存前通过 ImageIO 下采样到最长边 256 px。
2. LRU 容量由 12 张收紧为 4 张，并增加 1 MB 解码成本硬上限；超预算图片允许本次显示但不驻留。
3. 缓存键改为 SHA-256 摘要，不再为历史条目长期持有原始封面 `Data`；全部音乐来源清空后主动清理缓存。
4. 主色提取移除全局 Core Image / Metal 上下文，改为 ImageIO 先缩到 32 px，再通过 4 KB RGBA 缓冲区在 CPU 上计算平均色。
5. 长稳脚本升级为 schema 2，同时采样 RSS 与 macOS physical footprint，并对两者分别执行 `15%` 门禁。
