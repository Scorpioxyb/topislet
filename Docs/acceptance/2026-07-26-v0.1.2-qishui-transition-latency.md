# v0.1.2 汽水切歌原子加载延迟优化

日期：2026-07-26

## 目标与约束

缩短汽水音乐切歌后歌名、歌手、专辑、时长、进度和封面的完整显示延迟，同时保持原子更新：任何新歌名配旧歌手、旧专辑、旧时长或旧封面的过渡状态都不能进入岛内 UI。

## 源数据时序

汽水切歌后，MediaRemote 客户端会先给出混合过渡包，再给出完整新曲包。本机样本中：

- 控制进程开始后约 282ms：新歌名已经出现，但歌手、专辑、时长和封面仍属于上一首。
- 约 812ms：歌名、歌手、专辑、时长和封面全部切到新曲。

因此，直接发布第一个包虽然视觉上更早，但会制造错误信息，不能作为优化方案。零延迟也受汽水提供完整元数据的时间约束。

## 原因与修复

旧路径的长期 `stream-client com.soda.music` 使用 `--no-artwork`，每次切歌需要在收到状态变化后额外启动一个 `get-client` 进程读取封面。这个补取路径与汽水完整元数据到达时间叠加，增加了进程启动、JSON 读取和调度延迟。

最终方案：

1. 汽水专属状态流直接携带压缩封面，不再使用 `--no-artwork`。
2. 完整状态流包已经包含歌手和封面时，不再安排冗余元数据补取。
3. 原有事务门控保持不变：任何字段仍沿用上一首时继续等待，只有完整新曲包可以一次性发布。
4. 同步补取仍作为状态流缺字段时的降级路径，来源 PID、曲目身份和请求代次门禁不变。

## 同事件 A/B

旧安装版与新 Debug 候选同时订阅同一个汽水客户端，每轮只发送一次“下一首”，用同一个控制完成时间作为基线，记录两条状态流首次发布完整新曲的时间。

| 样本 | 旧路径 | 新路径 | 减少 |
| --- | ---: | ---: | ---: |
| 1 | 562ms | 328ms | 234ms |
| 2 | 570ms | 342ms | 228ms |
| 3 | 568ms | 338ms | 230ms |
| 平均 | 566.7ms | 336.0ms | 230.7ms（40.7%） |

三个样本的新旧路径最终都发布相同的完整曲目身份和真实封面，没有发布混合过渡包。

## 最终 Release 安装版

重新构建、签名并安装 `/Applications/顶屿.app` 后，状态流参数确认为：

```text
stream-client com.soda.music --debounce=40 --no-diff
```

不再包含 `--no-artwork`。三次连续实测完整发布延迟为：

- 344ms
- 343ms
- 345ms

平均 344ms，极差 2ms。相对旧路径 566.7ms 基线减少约 39.3%。
